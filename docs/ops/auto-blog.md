# ブログ記事の自動作成パイプライン（2026-11-14 稼働）

人間がやるのは **届いたメールで本文を読み、「公開する」→ GitHub で「Merge pull request」を押す** ことだけ（スマホで完結。GitHub にログインしておく）。
文章を直したいときとサムネイルを差し替えたいときだけ CMS を使う。
それ以外（ネタ選び・調査・執筆・仮サムネ・下書き登録・メール・チェック予定の登録）は自動。

## 流れ

```
3 日ごと 6:00 JST  クラウドの定期エージェント（Claude）が起動
   │  ダッシュボード（復号した全データ）、既存記事、10 月のテーマ一覧を読む
   │  最新ニュース・同業サイト・ガイドラインを Web で調査してネタを 1 つ選び、運営者視点で記事を書く
   │  ブランチ cms/blog/<slug> に content/blog/<slug>.md と content/.draft-notes/<slug>.md を push
   ▼
GitHub Actions（draft-article.yml）
   │  仮サムネイル blog/uploads/<slug>.png を生成してコミット
   │  PR（ラベル decap-cms/draft）を確認し、確認メールを送る
   ▼
メール「【要確認】ブログ下書き: <タイトル>」が届く（Gmail）。本文に記事の全文が入っている
   │  ★人間: メールで全文を読む → 「公開する」ボタン → GitHub の PR ページで緑の「Merge pull request」→「Confirm merge」
   │     没にするなら同じページの「Close pull request」。文章やサムネを直すときだけ CMS のワークフローへ
   │  （Vercel の /api/review によるワンタップ公開も実装済みだが、Vercel アカウントの 2 段階認証が復旧するまで未使用）
   ▼
main にマージ → build-blog.yml が記事 HTML・一覧・sitemap を生成 → 本番に反映
   │
   ▼
翌朝 6:30 ダッシュボード更新。2〜4 週間後に「検索から来られたページ」で効果が見える
```

エージェントは Google カレンダーに「記事チェック: <タイトル>」の予定（翌日 10:00）も入れる。

## エージェントへの指示（定期エージェントはこの節に従う）

あなたは「みのる歯科」（埼玉県東松山市沢口町の歯科医院）の Web サイト運営者（院長の次男）の代わりにブログ記事の下書きを 1 本作る。リポジトリはチェックアウト済み。

### 0. 準備
1. `git fetch origin` し、`origin/main` を最新にする。日付は `TZ=Asia/Tokyo date +%F` で取る
2. `docs/ops/blog-workflow.md` の「② 下書きを書く」「③ セルフチェック」を読む。ここに書き方と医療情報の線引きがある
3. 未公開の下書きが溜まっていないか確認する: `git ls-remote --heads origin 'cms/blog/*'` で 3 本以上あれば、**新しい記事は作らず終了**する（その旨だけ出力）

### 1. ネタを選ぶ（1 つ）
まずダッシュボードの全データを読む: 環境変数 `DASHBOARD_PASSWORD` があれば `node scripts/decrypt-dashboard-data.js` を実行すると `dashboard/data.json` ができる（訪問者数・流入チャネル・検索キーワード・ページ別・地域・広告・キーイベント）。このファイルとパスワードは絶対にコミット・出力・記事や調査メモへ転記しない（data.json は .gitignore 済み）。環境変数がない・復号できないときは `dashboard/insights.json`（検索キーワード・記事別閲覧数だけの平文）で進める。

読むもの: 復号した `dashboard/data.json`（または `insights.json`）、`blog-posts.json`（公開済み記事）、`content/blog/*.md`（公開済み本文）、`docs/aieo-seo/topics.md`（2026-10 に作ったテーマ一覧 10 本。骨子と想定検索語つき）、`git ls-remote --heads origin 'cms/blog/*'`（作成中）

優先順位:
1. ダッシュボードの検索キーワードで、表示回数があるのにクリックが少なく、既存記事で正面から答えていないもの（例: 「東松山 歯医者 日曜日」→ 休診日と急患時の相談先、「子供 歯磨き」→ 年齢別の仕上げ磨き）
2. `docs/aieo-seo/topics.md` の未着手テーマ。公開済み記事・作成中ブランチと題材が重なるものは除く。時期の指定（医療費控除は 1〜3 月、学校歯科健診は 6 月前など）があればそれに合わせる。使うときは一覧の「骨子」「想定する検索」を土台にする
3. 下の「調査」で見つけた、いま話題になっていること・季節の話題（直近のニュース、学会や厚労省の新しい発表、同業サイトで最近よく扱われている疑問）
4. 地域名を自然に入れられるテーマは、同じ価値なら優先する

既存記事・作成中ブランチと同じテーマは選ばない。タイトルは検索されそうな言葉を含め、32 文字以内を目安にする。

### 2. 調査する（ネタ決めの前後で行う）
WebSearch で候補を探し、WebFetch で原文を読む（2026-11-15 からクラウド環境のネットワークはフルアクセス。公式ページ・ニュース・他院ブログを直接読める）。万一開けないサイトがあれば検索結果の要約と複数の検索で裏を取り、確認しきれない数字・時間・電話番号は本文に書かず「公式ページで確認を」と案内する。

調べること（毎回この 4 点）:
1. **最新ニュース**: 直近 1〜3 か月の歯科・口腔ケア関連の報道、厚労省・学会の発表、季節の話題（例: 学校歯科健診の時期、インフルエンザ流行期と口腔ケア、年末年始の休診、花粉症と口呼吸、新年度の子どもの歯）。検索例: 「歯科 ニュース 2026年11月」「口腔ケア 最新 研究 発表」「厚生労働省 歯科 発表」。時期に合うネタがあれば優先候補にする
2. **同業の歯科医院サイト・ブログ**: 全国と近隣（東松山・比企・川越・熊谷）の歯科医院ブログで最近よく書かれている話題、患者からの質問として挙がっているもの。「何が今読まれているか」「どんな疑問が多いか」の参考にする。**他院の文章・構成・言い回しを写さない**。他院のサイトは事実の出典にもしない（事実は一次情報で裏取り）
3. **ガイドラインの最新版**: 書くテーマについて、学会推奨や公的基準が近年改定されていないか確認する（例: 2023 年の 4 学会によるフッ化物配合歯磨剤の推奨）。古い基準で書かない
4. **一次情報での裏取り**: 記事に書く数字・基準は、厚生労働省 e-ヘルスネット、日本歯科医師会、日本小児歯科学会、日本歯周病学会、日本口腔衛生学会、大学病院・学会の一般向けページで確認できたものだけ使う。確認できなければ数字を書かない

調査の要点を `content/.draft-notes/<slug>.md` に残す: ネタを選んだ理由、ニュースで見たこと（2〜3 行）、同業サイトで多かった話題（2〜3 行）、参考 URL、チェックリストの自己確認。ダッシュボードの数字はキーワードの表示回数・順位程度にとどめ、広告費や訪問者数の合計は書かない（このメモは PR とメールに転記される）

### 3. 書く
- ファイル: `content/blog/<slug>.md`。slug は英小文字・数字・ハイフンのみ
- frontmatter（この順・この形式）:
  ```
  ---
  slug: <slug>
  title: <タイトル>
  author: サイト運営
  date: <今日 YYYY-MM-DD>
  tags: <既存タグから 1〜2 個: 予防歯科 / 定期検診 / 歯磨き / 虫歯予防 / 小児歯科 / 歯周病 / 入れ歯 / 歯の豆知識>
  image: /blog/uploads/<slug>.png
  summary: <100〜150 字。結論が分かる要約>
  ---
  ```
- 本文: 1,500〜2,500 字。見出しは `##`（3〜5 個）と `###`。運営者（歯科医ではない）の視点で患者側に寄り添う語り口。**筆者の自己紹介・立場表明は書かない**（「私は歯科医ではなく院長の息子です」「先にお断りすると」等は禁止。著者欄・開示文は記事末尾に自動で付く）。専門判断が要る箇所は「歯科医院で相談を」と書く
- 冒頭 2〜3 行で「誰のどんな悩みに答えるか」。最後に受診を促す一文と当院の案内（予約制、平日 9:30〜13:00 / 14:30〜18:30、土曜 〜17:00、木日祝休診、電話 0493-24-9080、公式 LINE https://lin.ee/zFdXAeb、駐車場 4 台）。案内はトップページの記載と一致させる
- 出典を使ったら本文末に `## 参考` として URL を列挙
- 禁止: 「必ず」「絶対」「治る」「〜すべき」、治療法や薬の優劣、個別の診断、他院との比較、効果効能の断定
- 書き終えたら `docs/ops/blog-workflow.md` のチェックリストで自己確認し、結果を draft-notes に書く

### 4. 登録する
```bash
git checkout -b cms/blog/<slug> origin/main
git add content/blog/<slug>.md content/.draft-notes/<slug>.md
git commit -m "記事を追加: <slug>"
git push -u origin cms/blog/<slug>
```
- 続けて PR を作る。クラウド環境では `gh pr create`（GraphQL）が使えないので REST API で作る:
  ```bash
  PR=$(gh api -X POST repos/ttksaito/minoru-dental/pulls -f title="記事を追加: <slug>" -f head="cms/blog/<slug>" -f base=main -f body="Automatically generated by Decap CMS" --jq .number) \
    && gh api -X POST "repos/ttksaito/minoru-dental/issues/$PR/labels" -f "labels[]=decap-cms/draft"
  ```
  失敗しても止まらなくてよい（GitHub Actions `draft-article.yml` が仮サムネ生成と PR 作成を試みる）
- **main には直接コミットしない。PR をマージしない。公開は人間が行う**

### 5. 知らせる
Google カレンダーに予定を 1 件作る: 翌日 10:00〜10:15（Asia/Tokyo）、タイトル「記事チェック: <記事タイトル>」、本文に次を入れる:
- CMS のワークフロー: https://www.minoru-dental.jp/admin/#/workflow
- やること: 本文を読んで必要なら直す → サムネを変えたければアップロード → 「公開」
- 選んだ理由（1〜2 行）と参考にした情報源
- Claude Code に貼る文: `content/blog/<slug>.md を docs/ops/blog-workflow.md のチェックリストで確認して、直すべき点だけ挙げて。`

### 最後に出力すること
作った記事のタイトル・slug・ネタを選んだ理由・参考 URL・カレンダー登録の有無を簡潔に。

## 初回セットアップ（メールとワンタップ公開に必要な設定）

| 置き場所 | 名前 | 値 |
|---|---|---|
| GitHub Secrets | `REVIEW_SECRET` | （将来の Vercel ワンタップ公開用。現在は未使用）ランダムな長い文字列。Vercel と同じ値 |
| GitHub Secrets | `MAIL_USERNAME` | 送信に使う Gmail アドレス |
| GitHub Secrets | `MAIL_APP_PASSWORD` | その Gmail の「アプリ パスワード」（Google アカウント → セキュリティ → 2 段階認証プロセス → アプリ パスワード） |
| GitHub Secrets | `MAIL_TO` | 受け取るメールアドレス（スマホで見るもの） |
| Vercel 環境変数 | `REVIEW_SECRET` | （将来用）GitHub と同じ値 |
| Vercel 環境変数 | `GITHUB_PUBLISH_TOKEN` | （将来用）GitHub の Fine-grained personal access token。対象リポジトリ minoru-dental のみ、権限は Contents: Read and write、Pull requests: Read and write |

Vercel の 2 つを設定し、`draft-article.yml` のメール本文のボタン先を `https://minoru-dental.vercel.app/api/review?pr=<PR>&t=<HMAC>` に戻せば、GitHub を開かずにメールのリンク先だけで公開・没ができる（`api/review.js` は実装済み）。

GitHub Secrets は `gh secret set 名前 --body "値"`、Vercel は `vercel env add 名前 production`（または Vercel の Settings → Environment Variables）。
Secrets が未設定の間はメールが送られないだけで、CMS のワークフローからは従来どおり公開できる。

AI にダッシュボードの全データを読ませるには、定期エージェントの実行環境に環境変数 `DASHBOARD_PASSWORD`（GitHub Secrets と同じ値）を設定する。https://claude.ai/code の環境設定（Environments → Default）で登録できる。未設定でも `insights.json` で動く。

## 運用メモ（人間向け）

- 下書きが 3 本溜まるとエージェントは新規作成を止める。溜まったら CMS で公開するか、PR を閉じて（ブランチも削除）減らす
- 没にする = GitHub の PR ページで「Close pull request」。CMS の「ワークフロー」で削除してもよい
- 公開には GitHub へのログインが必要（スマホのブラウザで一度ログインしておけば以後は不要）
- 仮サムネイルを差し替えるには、CMS の記事画面の「サムネイル画像」から画像を上げ直すだけ
- 頻度や曜日を変える: https://claude.ai/code/routines/trig_01YAV7MzCNJ3kzaV7CBgbaAy （定期エージェント「ブログ下書きの自動作成（みのる歯科）」。3 日ごと 6:00 JST、モデル claude-sonnet-5-5。実行ログもここ）
- 書き方のルールを変える: `docs/ops/blog-workflow.md` と、このファイルの「エージェントへの指示」を直す。エージェントは毎回これを読む
- ネタの一覧を足す: `docs/aieo-seo/topics.md` に追記する（骨子と想定検索語を書いておくと、そのまま記事の土台になる）
- クラウド環境「Default」のネットワークアクセスは 2026-11-15 にフルアクセスへ変更済み（claude.ai/code の環境設定）。制限付きに戻すと WebFetch で読めないサイトが増える
- うまく動かないとき: GitHub の Actions タブ「記事下書きの仕上げ」のログ、または上の routines ページの実行ログ
- PR はエージェント自身が REST API で作る。GitHub Actions 側の PR 作成（予備）を効かせたい場合は、リポジトリの Settings → Actions → General → Workflow permissions で「Allow GitHub Actions to create and approve pull requests」をオンにする（2026-11-14 時点ではオフ。オンにしなくても運用は回る）
